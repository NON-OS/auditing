## Preconditions

- Hostile or compromised capsule holding FileSystem (bit 6) but not ForeignExec (bit 32)
- Guarded files exist (capsule_linux homes live in the vfs store)

## Description

named() in paths.rs has no OP_SEARCH arm, so reaches() serves OP_SEARCH without the ForeignExec check. Store::search scans name and content of every file including guarded ones, sorts by path and truncates to max_hits; the handler removes guarded hits only after truncation. A decoy file at a path that sorts after /linux-home holding a guess line, searched with max_hits=1, returns empty exactly when an earlier (guarded) path matches. Repeating with a growing prefix recovers a guarded line character by character. guard.rs states that listings and searches never show these trees to anyone.

## Impact

Breaks the stated separation of Linux-personality private data (wallet notes, password files) from other FileSystem holders. Needs a hostile or compromised FileSystem holder. Confidentiality only.

## Attack scenario

1. Attacker writes /zzz-decoy containing a guess line.
2. OP_SEARCH with content flag and max_hits=1: an empty reply means a guarded file matched.
3. Extend the guess one character at a time (681 queries for a 16 character line in the test).

## Evidence

Reproduced: yes.

- Reproduced twice, independently, on the host against the production search handler and gate rule, included by #[path] through userland/fs_proofs: the contents of a guarded test file (pass=Tr0ub4dor&3) were recovered in 681 queries; reaches(OP_SEARCH, no ForeignExec) is true, and OP_OPEN of the same guarded path is refused.
- NOT run: a booted image; mk_cap_check is a shim in host tests; whether any shipped capsule holds FileSystem without ForeignExec and is attackable was not enumerated.

## Remediation

Filter guarded hits inside Store::search before applying max_hits (or give OP_SEARCH a gate like the other ops), and add a regression test that a decoy cannot detect guarded content.

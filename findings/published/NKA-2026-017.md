## Preconditions

- Supply-chain change to vendored PQClean that no CI step would catch

## Description

Running the script at this commit prints 'pqclean tree drift: expected 2306482b..., actual 0fd27931...' and exits 1. PROVENANCE.md says CI verifies the pin on every push, but no caller exists in .github, nonos-ci, Makefile or nonos-verify. The pin hashes the committed listing, so it covers vendored bytes, not upstream identity. The project's own docs already record both facts.

## Impact

A stated tamper control for the vendored ML-DSA/ML-KEM code is not operating. Content check: the compiled dirs (ml-dsa-65, ml-kem-512/768/1024, common) are identical to PQClean upstream 0586a82, so no tampering was found.

## Attack scenario

1. A change to vendored PQClean sources is merged.
2. No CI job runs the pin check.
3. The change ships unless a reviewer notices.

## Evidence

Reproduced: yes.

- Run twice, independently: the script exits 1 with its drift message, and diff -rq of the compiled directories against upstream PQClean at 0586a82 shows no difference.
- Documented by the project (randomness-algorithms.md:44-47).

## Remediation

Regenerate the pin, wire the script into CI as a required job, and record the upstream commit of the snapshot in PROVENANCE.md.

## Preconditions

- Capsule must pass the spawn gate: publisher-tier capsule with a vendor-issued publisher certificate, signed manifest and an attestation under the vendor root or a root the person enrolled (kernel:src/kernel_core/process_spawn/capsule_spawn/runner/tier.rs:20-26, attest_gate.rs:19-30)
- Chain to a forged page-table entry rests on frame adjacency, not shown on a kernel

## Description

apply_relative_relocations checks r_offset only against the writable PT_LOAD range in virtual terms, translates one address, and does one 8-byte store at DIRECTMAP_BASE+pa. With (r_offset & 0xfff) > 0xff8 the store crosses the end of the physical frame into whichever frame follows. Value is base + r_addend, both chosen by the ELF. No alignment or page-crossing check exists on the x86_64 user path (the aarch64 boot relocator has one: kernel:src/arch/aarch64/boot/relocate/apply.rs:49). The next-fit allocator hands out ascending frames and populate_page allocates the data frame before the page-table frame, so a table frame can follow the data frame (traced, not run).

## Impact

Primitive reproduced on host: up to 7 bytes of attacker-chosen data written into another frame (in the test, the read-only segment page). If the next frame is a page table or another process's frame, kernel-controlled memory is written, which would be a user-controlled PTE (High). Only reachable by an enrolled third-party capsule's author; not by A1 without a publisher certificate, not by A2.

## Attack scenario

1. Author builds a PIE or ET_EXEC capsule with a writable multi-page PT_LOAD and a RELATIVE entry at r_offset page_start+0xffc or +0xfff.
2. The capsule is published and enrolled; the loader runs the relocation after mapping the segment.
3. The store spills into the next physical frame; the loader returns Ok.

## Evidence

Reproduced: yes.

- Host harness with the kernel's src/elf copied unmodified and stubs for memory, paging and SMP, built and run twice, independently: aligned 0x1ff8 writes frame61 only; straddle 0x1ffc writes 4 bytes into frame62 (the physically next frame) and returns Ok. The harness needed three small glue fixes to compile; none touches kernel code.
- A model of the allocator and page-table steps, which is not the kernel's code, produced a forged PT[0]=0x12345007. It shows the chain is plausible, and is not evidence that it happens in a running kernel.
- NOT run: any boot, the real allocator adjacency, whether the direct map of the next frame is writable, main.

## Remediation

Reject r_offset with (r_offset & 7) != 0 or crossing a page; or write byte-wise through per-page translation; apply the same check to every direct-map store in the loader.

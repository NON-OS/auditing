## Preconditions

- Capsule holds the capability class MkCapsuleLoad requires (CoreExec, IPC and Memory together, the same class an ordinary loader-using capsule already holds)
- Most severe on a single-CPU machine or when the kernel is otherwise pinned to one core; on a multi-core machine a victim thread on a different core was not stalled by a single call

## Description

sys_capsule_load copies its five input buffers (an ELF image, a certificate, a manifest, a trailer and arguments, up to 16 MiB each) from the caller into freshly zeroed kernel buffers before any manifest or signature check runs. The copy loop does not yield, and because a kernel-mode tick does not switch threads, nothing else on that CPU runs until the whole copy finishes.

## Impact

A single call with five 16 MiB buffers measured 143-999 ms of wall time across repeated boots on one CPU, during which a second thread on the same CPU made no progress. On a two-CPU boot a single call did not stall a victim thread on the other core, but repeating the call from several attacker threads across both cores did add measurable delay to the victim. The cost is bounded per call and needs capabilities an ordinary capsule-loading service already holds.

## Attack scenario

1. A capsule holding the capsule-load capability calls MkCapsuleLoad with five buffers near the 16 MiB limit, repeatedly, back to back.
2. On a single-CPU machine, every other thread on that CPU is starved for the duration of each call.
3. On a multi-CPU machine, one attacker thread per CPU reproduces a smaller version of the same effect.

## Evidence

Reproduced: yes.

- Measured directly from kernel timestamps on a booted development build under KVM, single CPU, six separate boots: a victim thread's scheduling gap during one five-times-16-MiB call was 143, 144, 233, 271, 334 and 1001 ms; the call's own measured duration matched within 2 ms each time.
- The same test with five 4 MiB buffers gave victim gaps of 17-221 ms across the six boots; with five 1 MiB buffers, about 4 ms. A spinning victim thread with no attacker call running had a baseline gap of about 8 ms, confirming the delay tracks buffer size.
- On a two-CPU boot, six repeats: the call itself took 168-577 ms, but a victim thread scheduled on the other CPU saw a 0-1 ms gap for a single attacker call; with four attacker threads spread across both CPUs the victim gap rose to 53-72 ms.
- Not shown: a victim in a different capsule than the attacker (an attempted test of this was broken and discarded); the published release image specifically, rather than a development build of the same commit.

## Remediation

Validate buffer sizes, or at least the total, before copying; if large copies cannot be avoided, run them in a way that lets the scheduler interleave other work on the same CPU rather than holding it for the whole operation.

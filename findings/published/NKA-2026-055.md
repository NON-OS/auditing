## Description

The project's machine-checked proofs for the TPM rollback-floor code are presented as proving the response-handling logic sound. Reading the actual proof harness shows it calls the function that decides whether a TPM response counts as successful, but only to confirm the call does not crash; it never asserts anything about the result that function returns. A deliberately introduced defect in that function (changing it so it no longer checks the TPM's own response code, only the response's length) still passes every proof in the harness, because nothing in the harness depends on that check. The project's ordinary unit tests do catch the same deliberately introduced defect.

## Impact

The response-code check this proof is meant to cover is real and currently correct in the shipped code; this check found no defect in the code itself. What it found is that the formal proof does not actually constrain this property, so a future change that broke it, specifically in a way the unit tests did not also happen to cover, would not be caught by the proof suite the project's own documentation points to as covering it. The function this gap concerns decides whether the rollback floor was actually raised; treating a TPM error as success here would silently skip a floor raise rather than cause an immediate failure.

## Attack scenario

1. A future change alters the function that decides whether a TPM response counts as successful, in a way that happens not to be caught by the project's unit tests.
2. The project's formal proof suite, run as part of its own verification pipeline, reports success, because the harness never checked this property in the first place.

## Evidence

Reproduced: yes.

- Read the proof harness directly: it calls the response-success function and discards the result, so Kani (the tool used to check the proofs) only confirms the call itself does not panic, not anything about what it returns.
- Deliberately changed the response-success function, in a scratch copy, to drop its check of the TPM's own response code and keep only a length check, then re-ran the full proof suite: all three of the harness's proofs still reported success, with zero failures.
- Ran the project's own unit tests against the same deliberately changed function: two tests failed, confirming the unit-test suite does cover this property even though the formal-proof suite does not.
- Checked three other, related defects introduced the same way in a nearby parsing function (a shifted byte offset, a dropped length check, and accepting any response code at a different call site): all three were caught by the proof suite, showing the gap is specific to the one function and not the whole harness.
- Not checked: whether the project's continuous-integration configuration runs the unit test suite for this component at all, separately from the proof suite; the public verification notes for this component were read and name only the proof run.

## Remediation

Extend the proof harness to assert the actual outcome of the response-success check (for example, that a response with a non-zero response code is never treated as successful), not merely that the call does not crash.

## Preconditions

- Capsule must pass the spawn gate: publisher-tier capsule with a vendor-issued publisher certificate, signed manifest and an attestation under the vendor root or a root the person enrolled (kernel:src/kernel_core/process_spawn/capsule_spawn/runner/tier.rs:20-26, attest_gate.rs:19-30)

## Description

entry_point does base_addr + e_entry with a plain add; the release profile has overflow-checks=true and panic=abort, and nothing checks e_entry against a PT_LOAD. Second symptom: enforce_relro walks PT_GNU_RELRO page by page with no bound to the image and no shootdown service, under the global ELF_LOADER lock.

## Impact

Availability: one enrolled capsule can halt the machine at spawn (panic = abort), or block every other spawn while a long RELRO walk runs. No confidentiality or integrity effect. Same gate precondition as NKA-2026-020.

## Attack scenario

1. Author sets e_entry = 0xffffffffffffffff in a PIE capsule and has it enrolled.
2. On spawn the loader maps the image, then entry_point overflows and the kernel panics and halts.

## Evidence

Reproduced: yes.

- Host harness (real src/elf copy, release profile with overflow-checks): `h_elf entry` panics at virt.rs:82 'attempt to add with overflow'; 2M-input mutation fuzz gave 700 panics all at that site; a second, independent run of 20M inputs gave 5,879 panics. RELRO time linear (memsz 2^32 about 23 ms with a stub translate).
- NOT run: any boot, the kernel panic path, real RELRO cost at 2^47 (extrapolated).

## Remediation

Use checked_add and return an ElfError; require e_entry inside an executable PT_LOAD; bound RELRO to the image's own segments.

## Preconditions

- Hostile capsule holding the IPC bit
- Target service whose required caps the attacker holds and that is not held_to another capsule

## Description

try_enqueue admits when queue length < capacity and the byte budget admits. The byte share is per sender (8 MiB, inbox 16 MiB), but 1024 one-byte messages cost about 144 KB, so the count fills first. The doc says a flood from one sender fills at most half of any inbox; that holds for bytes, not slots. The share is keyed by pid and a thread is its own pid, so threads also bypass the byte share.

## Impact

While the flood continues, other senders get EAGAIN/EBUSY to the target service. Availability of one service at a time; no data effect.

## Attack scenario

1. Attacker sends 1-byte messages with MkIpcSend to a service whose gate needs only IPC.
2. 1024 messages fill the inbox; every other sender is refused until the server drains.
3. The server cannot tell senders apart by count and must dequeue each junk message.

## Evidence

Reproduced: yes.

- A host model built against the real budget.rs showed the count limit is reached before the byte limit: 1024 of 1024 one-byte messages admitted from one sender, 144,384 bytes held.
- Confirmed by an independent code reading.
- Reproduced on a booted kernel: one sender filled its own inbox with 1,024 one-byte messages (all accepted), then a second, unrelated process's one-byte send to that same inbox was refused (rc=-16, EBUSY).

## Remediation

Add a per-sender slot limit (keyed on thread group, not pid) of at most half the capacity, or correct the documented claim to say bytes only.

## Description

The bootloader has its own, separate dependency lockfile from the kernel's root lockfile. Running the project's own advisory scanner against the root lockfile passes cleanly, but the same scanner run against the bootloader's own lockfile fails: it pins version 0.8.0 of a crate with nine published unsound-usage advisories (fixed in 0.9.4 and later) covering several of its collection types, and a separately yanked crate version. The project's supply-chain CI configuration only points at the root lockfile, so this never surfaces there.

## Impact

On the code path actually used, the bootloader only calls the one, unaffected part of the flagged crate (a simple vector type), and the advisories concern other types in the same crate the bootloader does not use; this check found no path by which the bootloader is actually exposed to the unsound functions. The finding is that the dependency itself, and the scan surface that should have flagged it, are currently incomplete: a future change that does start using one of the flagged types would ship with no automated warning, because nothing currently checks that lockfile.

## Attack scenario

1. A maintainer relies on the project's supply-chain CI passing as confirmation that no component's pinned dependencies carry open advisories.
2. The bootloader's own lockfile, built and shipped separately from the root lockfile, is never scanned, so an advisory affecting it would not be caught even if a future change began using the affected code.

## Evidence

Reproduced: yes.

- Ran the project's own advisory scanner (cargo-deny) against the root lockfile: clean, no errors.
- Ran the same scanner against the bootloader's own lockfile: failed, naming nine unsound-usage advisories against one pinned crate version (covering its double-ended queue, index map, single-producer/single-consumer queue, sorted linked list, a pool-view type, a lock-free stack, and a panic-safety issue in its Drop implementation) and one separately yanked crate version.
- Traced every call into the flagged crate from the bootloader's own source: the only use found is the crate's plain fixed-capacity vector type, which is not one of the types named in any of the nine advisories.
- The advisories whose unsound functions require unwinding to trigger were also checked against the bootloader's own panic strategy, which aborts rather than unwinds in this build configuration, removing that specific route; this was not verified against every build configuration that produces a shipped bootloader.
- The project's bans, license and source checks were also run against the root lockfile (clean) and spot-checked against a sample of other sealed lockfiles in the tree (consistent, sourced from crates.io or an explicitly pinned alternate source), though the roughly 100 other sealed lockfiles in the tree were not all scanned individually in this check.

## Remediation

Add the bootloader's lockfile, and the project's other sealed lockfiles, to the supply-chain CI's scan scope so an advisory against any of them is caught automatically; separately, consider moving off the flagged crate version regardless, since the unused-API argument depends on usage staying as it is today.
